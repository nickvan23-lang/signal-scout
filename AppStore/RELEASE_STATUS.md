## Experimental Duo readback

PR #5 replaces the rejected command's readback path with `UIHingeInteraction` observations inside the app. The observer is compiled only with `DUO_DIAGNOSTICS` and starts only when given a valid launch-session UUID. Each host request has a unique request ID; only a real matching UIKit callback can advance the event sequence and observation timestamp. The host requires the launched process ID, exact session/request identity, a new sequence, a foreground-active scene, finite angle and time values, and a fresh callback after the request. It checks observations before and after each screenshot, with the same scene and display identity across that interval. Nil or background observations invalidate availability, and snapshot-write failures stop the diagnostic session instead of leaving reusable valid evidence.

Requested hinge targets are never substituted for measured angles. The existing one-degree angle tolerance and matching hinge status remain required. Portable tests include mocked observer exchanges and failure cases. The native observer compiled successfully in three supported-readback attempts. Both fresh-fixture attempts reached boot readiness but stalled during installation, so live callback delivery and fold capture remain unverified. Further native validation requires a healthy Xcode 27.1 runner; if the run-owned simulator still exists, cleanup must be limited to the exact UUID in its ownership receipt. The experimental workflow still removes `UIRequiresFullScreen` and labels its configuration. Rendered screenshot orientation and visual layout require separate review, and physical BLE reception remains unverified by this workflow.

## Signed-release capability

The repository has a working simulator verification workflow, but no automated signed iOS release route was found in the inspected workflow and script files. `ios-release-qa.yml` explicitly sets `CODE_SIGNING_ALLOWED=NO` and runs tests; it does not archive, export, or upload an App Store binary. The Pages workflow publishes the support site only.

`ExportOptions-AppStore.plist` and `ExportOptions-Upload.plist` retain Xcode settings for automatic signing and App Store export/upload. These configuration files are useful inputs for an authenticated Xcode release on a Mac; they do not provide a signing identity, provisioning profile, or App Store Connect authentication. No credential stores were inspected to infer that those capabilities exist.

The current execution environment can compile the portable Swift core on Linux and can run simulator CI on a hosted Mac. It has no connected Mac/Xcode control service or authenticated signing/upload route available for producing the repaired distribution binary. The next release requires access to a Mac or configured release runner with the app's authorized distribution signing identity, matching provisioning, and App Store Connect authentication. The source still specifies build **8**; verify the existing Apple build inventory before selecting an unused number for the corrected binary. The older unsigned experimental build does not establish that a number is free or that a signed release exists.
